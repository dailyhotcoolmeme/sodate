# 문토 API 최대 목록 수 변경 및 워치독 재실행 루프

## 근거

- 관리자 Gmail 10/30 `긴급 1건 — 문토`, GitHub 실패 메일 확인. 다른 계정 중복 없음.
- 정기 수집 40970022359 및 자동 재시도 40974784163: 프립/rest 성공, 문토 실패.
- 실제 공식 `/api/web/v1/socialing/section?type=default&categoryId=12&limit=300`
  응답 HTTP 400: `limit must not be greater than 200`.
- limit=200, offset=0은 200개, offset=200은 22개, offset=222는 빈 목록을 반환.
  22개 페이지도 hasMore=true이므로 짧은 페이지라고 중단하면 안 된다.
- 기존 `_get`은 HTTP 400을 None으로 반환했고 목록 함수가 빈 목록으로 재시도했다.

## 수정 및 보호

- 200개씩 offset 페이지 수집, ID 중복 제거. 빈 최종 페이지/hasMore=false까지 확인.
- 후속 페이지 실패·반복 페이지·상세 조회/파싱 실패 시 collection_complete=false,
  DELETE_STALE=false로 미래 기존 일정이 누락됐다는 이유로 삭제되지 않도록 한다.
- verified=true 보호와 변경된 값만 저장하는 공통 경로는 유지한다.
- 문토 전용 재검증은 기존 main.py --group=munto와 동일 R2 설정을 사용한다.
  다른 업체/Apify/후속 알림은 실행하지 않는다.
- 워치독은 최근 실제 실패 실행을 스케줄 정지로 오인해 전체 크롤을 반복했다.
  최근 16시간 내 실패 실행이면 장애 경보를 유지하되 전체 자동 재실행은 보류한다.
  진짜 오래 실행이 없는 경우의 자동 재발화는 유지하며, GH 조회 실패 시도 보류한다.

## 실제 데이터 대조 및 추가 보완

- 기존 자동 정리 경로에서 지난 일정 1건과 원본 소멸 확인 197건을 삭제했다.
  복구 전후 스냅샷 대조 결과 이 중 미래 일정은 35건이며, 35건 전부 공식 상세 API의
  404/410을 다시 확인했다. 추측 복구나 추가 수동 삭제는 하지 않았다.
- 살아 있거나 확인 불가인 삭제 후보 155건은 보존했다. 이 중 원본 날짜가 바뀐 5건이
  기존 날짜로 남은 문제를 전체 대조에서 발견했다. 원본 상세 startDate를 직접 확인하고
  기존 ID/URL/verified=false/기존 날짜 조건으로만 날짜와 원본 제목을 갱신했다.
  대상 원본 ID: 697313, 689633, 697009, 684726, 701933.
- 재발 방지: is_gone()에서 200으로 확인한 누락 회차 원본을 보관하고 공통 저장 후
  날짜 변경을 다시 반영한다. 시간대 없는 원본은 추측하지 않고, 날짜 변경 시 가격도
  해당 원본의 값만 사용한다. 동시 수동 수정으로 조건이 바뀐 행은 수정하지 않는다.
- 마감 대조 차이 4건은 RECRUITING이지만 남녀 잔여석이 모두 0인 실제 마감이었다.
  일반 수집이 이를 신청 가능으로 되돌리지 않도록 경량 갱신과 `_munto_closed`를 공유했다.
  정원 미상(None)은 매진으로 추정하지 않는다.
- 최종 DB 1732→1778행. 공개 미래 일정 1734건 전부를 점검:
  원본이 살아 있는 1729건의 날짜/가격/마감 일치, 원본 소멸 5건은 이미 마감 상태 확인.
  공식 목록에 없는 행은 상세 API로 재검증했다. 추가 불일치 0건.

  신규/기존 표본 6건도 상세 원본과 공개 API까지 직접 대조했다.
- 읽기 전용 워치독 업체 장애/빈 수집/급락 검사 결과 []로 문토 수집 장애 해소 확인.
