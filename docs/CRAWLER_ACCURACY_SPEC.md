## ⚠️ 전략 전환 — 오너 결정 (2026-06-06)

**"100% 완전자동 크롤링으로 정확도 보장은 불가"** 가 16곳 실측으로 확정됨(구조적 데이터 부재·자유텍스트 라벨·실시간 휘발성). 따라서:

> **데이터 입력 = 오너 직접 등록(수동) 방식으로 전환.** 단 **"아주 편하게" 등록**되도록 만드는 게 핵심 요구사항.

**크롤러의 새 역할 = 정답 소스(X) → 등록 폼 자동 채움(prefill) 엔진(O).**
- 오너가 URL(또는 이미지) 붙여넣기 → 크롤러가 제목·이미지·날짜·가격·지역 추출해 **폼에 미리 채움**
- 오너는 자동화가 못 잡는 **정확도(품절·좌석·최종확인)만 빠르게 검수/수정** 후 저장 → 속도+정확도 동시 확보
- 즉 이 문서의 load_option.cm·cascade 분석은 **버려지지 않고 prefill 추출기로 재활용**됨.

**영향(추후 반영 필요):** `CLAUDE.md` §🚫3("업체 직접 등록 금지")·핵심구조("크롤링→DB→앱"), `docs/PRD.md` MVP scope — 등록 중심으로 수정 대상. 오너 확인 후 갱신.

**다음 설계:** 등록 UX("아주 편하게")를 별도 설계서로. → `docs/ADMIN_REGISTRATION_SPEC.md`(예정).

## 1. 문제 재정의 (정찰로 확정)

기존 가설은 "정확한 값이 신청 플로우 안쪽에 숨어 있어 크롤링 불가"였으나, 실측 결과:

> **대부분 업체는 일정·가격·성비·좌석을 페이지 텍스트 또는 옵션/ API에 노출하고 있다.**
> 진짜 원인은 "값이 없다"가 아니라 **현재 스크래퍼가 그 구조화된 값을 못 잡고(brittle 정규식·요일 하드코딩) 있다는 것.**
> 정밀값이 실제로 "존재하지 않는" 업체는 **러브매칭 1곳뿐**(구매 후 매니저가 카톡으로 일정 조율).

## 2.5. ⭐ 검증된 정답 소스 — imweb `load_option.cm` (2026-06-05 실측)

"버튼 눌렀을 때 나오는 값과 일치하느냐"를 인썸파티로 실측 검증한 결과:

- **정적 DOM/페이지 텍스트 스크래핑은 실제와 불일치.** 원인:
  1. 옵션이 정적 DOM에 없음(`<select>`/li 스크래핑 → 0개). 구매 클릭 시 XHR로 로드됨.
  2. 페이지의 `남103:여101 참여53커플` 류 큰 숫자는 **월별 누적 history 통계**지 좌석이 아님 → 좌석으로 긁으면 오답.
  3. DOM의 `[옵션] 04/20(토)` 평면 리스트엔 과거·품절 옵션 잔재가 섞임.
- **정답 소스 = `POST /shop/load_option.cm` (body: `type=prod&prod_idx={idx}`)**
  - 브라우저 없이 httpx로 **직접 replay 성공**(200). 응답은 옵션 HTML.
  - 응답의 `날짜(필수)` 드롭다운 = **유저가 실제 선택 가능한 일정만** 정확히 포함.
  - 실측: prod175→`6월 13일(토)`, prod181→`6월 6일(토)`, prod209→없음(마감). ← 기존 스크래핑(6/6·6/13·4/16 혼재)과 명백히 다름.
  - 종속 구조: `날짜 → 성별 → 할인티켓`. 성별/잔여는 날짜 선택 후 cascade(추가 호출/클라이언트)로 노출.
- **imweb 공통**: `OMS_auth.cm`(토큰)·`load_option.cm`·`load_prod_additional_mobile.cm` 동일 엔드포인트군 → **imweb 업체 전체에 같은 방식 적용 가능.**

> 따라서 imweb 정답값 추출 = `load_option.cm` replay로 **선택가능 일정** 확보 → 날짜별로 성별 cascade 1회 더 호출해 **성별·잔여** 확보. 정적 스크래핑/페이지 텍스트는 보조로만.

### imweb 일반화 실측 — 4개 추가 (2026-06-05)
같은 `load_option.cm` 엔드포인트를 4개 업체에 적용. **엔드포인트는 imweb 공통(전부 200+옵션데이터)** 이나 데이터 현실은 제각각:
- **emotional_orange ✅ 깨끗한 2번째 성공**: idx55→`06/06,06/13,06/20,06/27`, idx46→6월 다수. 미래 일정 정확.
- **solooff ❌ 패턴 불일치**: 옵션이 `종류(회원권)/성별` 또는 **자유입력 "참가 희망 날짜를 적어주세요"** → 선택형 날짜 없음. 별도 처리(또는 제외) 필요.
- **lovecommunity / flipo ⚠️ 현재 라이브 상품이 폐기건뿐**: load_option이 **과거 날짜(1~2월, 4월) 잔재**를 그대로 반환. → load_option 결과도 **미래날짜 필터 필수**(스크래퍼의 `is_within_one_month`+`event_date>=now`가 흡수). 죽은 상품은 결과적으로 0건 emit.

> 교훈: load_option.cm은 imweb **공통 메커니즘**이지만 만능 아님. ① 미래날짜 필터 필수, ② 자유입력형(solooff)은 예외 처리, ③ 좌석은 페이지 렌더 블록에서(엔드포인트엔 없을 때 있음). 업체별 1회 실측 후 적용.

### 좌석(성별별) cascade 검증 — 완료 (인썸파티 prod175)
- 날짜 `6월 13일(토)` 선택 → 성별 옵션 `여성·남성` 노출, **잔여 `남 4/16 · 여 3/16`** 확보.
- 이 좌석 표기는 상품 페이지 스케줄 블록에도 동일하게 존재(`6월 13일(토) 남 4/16 여 3/16`) → `load_option.cm`의 일정과 **교차검증 일치**.
- 즉 imweb 추출 파이프라인: ① `load_option.cm`(일정 확정) ② 페이지 스케줄 블록/2차 옵션(성별·좌석) 교차검증.
- ⚠️ 미확정 1건: `4/16` 표기가 `신청수/정원`인지 `잔여/정원`인지 — 정원 다 찬 이벤트 1건으로 의미 최종 확정 필요(파싱 규칙에만 영향, 값 위치는 확정).

## 3. 핵심 설계 — imweb 옵션 통합 파서 (`imweb_option_parser`)

imweb 업체 9곳(solooff, lovecommunity, emotional_orange, flipo, secretsalon, seolrem, yeonin, inssumparty, lovecasting 중 imweb 계열)이
**동일 구조**(상품 = 회차묶음, 옵션 = 개별 일정×성별)를 쓰므로 **공용 파서 하나**로 처리한다.

### 3.1 파서 동작
1. Playwright로 상품 상세 진입 → 옵션 select/li가 lazy-load면 프로그램적으로 펼침(imweb `SITE_SHOP_DETAIL.selectOption` 또는 select 트리거).
2. 각 옵션 텍스트를 정규화 파싱:
   - **일시**: `4월18일 토요일 오후4시`, `04/20(토) 18:30`, `3월2일 오후6시` → KST datetime
   - **성별**: `남성/여성/남/여/삼성남성` → male|female
   - **테마/프로그램**: `와인파티/커피미팅/후기약속특가` → theme[]
   - **지역**: `삼성/수원/강남` → region
   - **품절/마감**: 옵션 disabled·`품절` 클래스 → is_closed
3. **좌석**: 옵션·본문의 `현재/정원` 패턴(`12/16`, `6/3`, `2/8`, `45/80`) 또는 성비 현재인원(`남1 여5`) 파싱.

### 3.2 출력
회차 1건 = `EventModel` 1건. (기존 모델 필드 그대로: event_date, gender, price_male/female, capacity_*, seats_left_*, theme, region, is_closed)

### 3.3 좌석/성비 추출 규칙
- `현재/정원` 형식 → `seats_left = max(0, 정원-현재)`
- `남N 여M` 누적 카운트 → 성비/현재인원
- 값 없으면 `None`(절대 추측/하드코딩 금지)

## 5. 정직성 원칙 (제품)

- 좌석은 휘발성이 크다 → **확실한 현재/정원 값이 있을 때만 숫자 표기**, 없으면 "마감임박"·"신청 페이지 확인"으로.
- 추측으로 채운 값(요일 하드코딩 등)은 **정확 파싱·Vision으로 대체하거나 비워둔다.** 틀린 정확값 < 정직한 공백.
- 앱 본질 = **모아보기 + 아웃링크**. 실시간 예약 보장이 아니므로 공백 UX 허용 가능.
