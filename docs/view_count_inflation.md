# 게시판 조회수 부양(가산) — 왜 넣었고, 언제 어떻게 걷어내나

> 2026-08-15 오너 지시로 도입. **앱이 활성화되면 걷어낼 것을 전제로 만든 장치**라
> 그 시점에 헤매지 않도록 남긴다.

## 한 줄 요약

게시글 상세에 보이는 조회수는 **실제 수치가 아니다.** DB에는 진짜 조회수만 쌓이고,
가산은 **화면에서만** 얹는다. 걷어낼 땐 함수 한 줄만 바꾸면 되고 데이터 정리는 필요 없다.

## 왜 넣었나

커뮤니티를 막 열어서 글당 실제 조회수가 한 자리~두 자리였다. 그대로 보이면 휑해 보이고,
사람이 없는 곳으로 읽혀 더 안 들어오는 악순환이 된다. 그래서 초기에만 수치를 부양한다.

## 지금 계산식

`app/lib/board.ts` 의 `displayViewCount()` 하나에 전부 모여 있다.

```
표시 = 실제 조회수 + (기본 가산 + 댓글수 × 70 + 지터) × 램프비율
```

| 조각 | 값 | 왜 이렇게 |
|---|---|---|
| 기본 가산 | 300~600 | 처음엔 500~1000 이었으나 최대 1,547 까지 올라가 초기 규모에 비해 과했다 |
| 구간(BANDS) | 30 | 300~600 을 댓글 수에 따라 31칸으로 나눠 뽑는다. 댓글이 많을수록 기본값도 커진다 |
| 댓글당 | 70 | 고정값. 랜덤으로 두면 순서가 뒤집힌다(아래 제약 참고) |
| 지터 | ±30 | 같은 댓글 수끼리 610/610 처럼 숫자가 겹쳐 조작 티가 나던 것을 흩뜨린다 |
| 램프 | 1시간 / 120스텝(30초) | 글 쓰자마자 수백이 찍히면 바로 티가 나서 서서히 차오르게 한다 |

값은 전부 **글 id 에서** 만든다(FNV-1a). 난수를 그때그때 뽑으면 새로고침할 때마다
숫자가 출렁여 즉시 들킨다. 같은 글은 같은 시각에 언제나 같은 숫자가 나온다.

### 램프 (서서히 차오르기)

- 글 작성 후 **1시간**에 걸쳐 가산분이 0 → 목표치까지 찬다. 1시간이 지난 글은 즉시 목표치.
- 30초마다 한 칸씩, 칸마다 가중치를 따로 뽑아 더하므로 **증가폭이 매번 다르다**.
  일정한 규칙으로 오르면 그것대로 티가 난다.
- **초반 가중**: 앞쪽 스텝일수록 가중치가 크다(2.3배 → 0.3배). 갓 올라온 글이 목록 맨
  위에 있을 때 조회가 몰리고 밀려나면서 완만해지는 실제 게시판 패턴에 맞춘 것.
- 가중치가 항상 양수라 **값이 줄어드는 일은 없다**(검증: 글 300개 × 30초 간격 121지점, 위반 0).
- 갓 쓴 글은 가산이 0이라 **실제 조회수만 보인다**(조회 1~3).

실제 진행 예(댓글 6개 글, 목표 819):

```
 0분 0 → 1분 24 → 3분 61 → 5분 131 → 12분 288 → 25분 510 → 45분 728 → 60분 813
증가폭  22    26     70      80       114       104        23
```

## ⚠️ 손댈 때 지켜야 할 제약

1. **`VIEW_JITTER × 2 < VIEW_PER_COMMENT`**
   지터 폭이 댓글당 가산보다 커지는 순간 "댓글 많은 글이 더 많이 읽혔다"가 깨진다.
   지금은 60 < 70 으로 아슬아슬하다. 지터를 키우거나 댓글당 가산을 줄이려면 둘 다 같이 봐야 한다.
2. **`VIEW_BANDS` 는 댓글 수 상한**. 이보다 댓글이 많으면 구간이 포화돼 그룹 간 여유가
   줄어든다(10 이었을 때 여유 43점까지 떨어져 순서가 뒤집혔다 → 30 으로 넓힘).
3. 순서 보장은 **성숙한 글끼리만** 의미가 있다. 램프 중인 새 글은 목표보다 낮아서
   1시간 지난 댓글 0개 글보다 낮게 나올 수 있다 — 실제 게시판도 그러므로 정상이다.
4. 조회수는 **글 상세에만** 보인다. 피드 목록에는 넣지 않았다(오너 선택).

## 📌 걷어낼 때

### 방법

`app/lib/board.ts` 의 `displayViewCount()` 본문을 한 줄로 바꾼다.

```ts
export function displayViewCount(post: { view_count?: number | null }): number {
  return post.view_count ?? 0
}
```

- DB(`board_posts.view_count`)는 처음부터 **진짜 조회수만** 담고 있다. 마이그레이션이나
  데이터 정리가 필요 없다.
- 조회수 증가는 `markViewed()` → Edge Function `view` → `increment_board_view` RPC 로
  이미 정상 동작 중이므로 건드릴 것이 없다.
- 상수(`VIEW_*`, `RAMP_*`)와 `rampRatio`, `seedOf` 는 같이 지우면 된다.

### 언제 걷어내나 — 판단 기준

한 번에 끄면 조회수가 갑자기 1/10 로 떨어져 오히려 이상해 보인다. 아래를 보고 판단할 것.

- **실제 조회수가 지금 가산 규모(300~800)에 근접**했는가. 인기 글이 실제로 300~500 을
  찍기 시작하면 가산이 무의미해진다.
- 그 전 단계로 **가산 폭만 단계적으로 낮추는** 방법이 있다. `VIEW_BASE_MIN/MAX` 와
  `VIEW_PER_COMMENT` 를 함께 줄이면 되고, 위 제약 1번만 지키면 된다.
  (예: 300~600 → 150~300, 댓글당 70 → 35)
- 갑자기 0 으로 만들 거면 실제 수치가 충분히 올라온 뒤가 좋다.

## 이력

- 2026-08-15 도입. 기본 500~1000 + 댓글당 120.
- 2026-08-15 규모 축소. 500~1000 → 300~600, 댓글당 120 → 70 (최대 1,547 이 과했음).
- 2026-08-15 지터 ±30 추가. 같은 댓글 수끼리 숫자가 겹쳐 조작 티가 나던 것 해소.
  이때 `VIEW_BANDS` 10 → 30 (지터가 그룹 간 여유를 잡아먹어 순서가 뒤집혀서).
- 2026-08-15 1시간 램프 추가. 글 쓰자마자 수백이 찍히던 것 해소. 초반 가중, 30초 스텝.
